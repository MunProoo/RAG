# 사내 문서 도우미(RAG) — AI 세미나 발표 노트

**대상:** 비전공자 포함 전체  
**분량:** 약 15~20분  
**프로젝트:** Open WebUI + 로컬 AI(Ollama) + 사내 문서 검색(RAG)

---

## 발표 흐름 (목차)

1. RAG와 “AI를 다시 학습시키는 것”의 차이  
2. 하네스 엔지니어링으로 관리한 프로젝트 구조  
3. 실제로 바뀐 점·좋아진 점  
   - (슬라이드 7–9) 검색의 진화: 벡터 → Hybrid(BM25+RRF) → Reranker  
4. 예상 질문(Q&A)

# 1. RAG와 AI 모델을 학습시키는 것의 차이

> **30초 요약:**  
> 우리는 AI에게 매뉴얼을 **외우게** 하지 않고, 질문할 때마다 **참고서를 펼쳐 보게** 했습니다. 그게 RAG입니다.

### 발표 포인트

- **RAG** = Retrieval-Augmented Generation  
  - 쉬운 말: **시험 볼 때 참고서를 펼쳐 보고 답하는 것**  
  - 매뉴얼·스펙 파일은 그대로 두고, 질문마다 “관련 페이지”를 찾아 붙여서 답을 만듦  
  - 답 옆에 **어느 문서에서 봤는지(출처)**를 달 수 있음

- **학습(파인튜닝·재학습)** = 모델 속을 바꾸는 것  
  - 쉬운 말: **참고서 내용을 머릿속에 다시 외우게 가르치는 것**  
  - 시간이 오래 걸리고, 좋은 학습 데이터·큰 GPU 비용이 필요함  
  - 매뉴얼이 자주 바뀌면 **또 다시 가르쳐야** 함

| 비교 | RAG (참고서) | 재학습 (외우기) |
|------|--------------|----------------|
| 문서가 바뀌면 | 문서만 다시 넣으면 됨 | 보통 다시 학습 |
| 출처 표시 | 하기 쉬움 | 어렵거나 불명확 |
| 비용·시간 | 상대적으로 적음 | 큼 |
| 이 프로젝트 | **선택** | 부담이 커서 비선택 |

### 우리가 RAG를 고른 이유 (한 줄씩)

- 사내 매뉴얼·스펙이 **자주 바뀜** → 외우게 하면 따라가기 힘듦  
- 직원에게 **“어디서 나온 말인지”**가 중요함  
- 큰 모델을 사내에서 매번 재학습하기엔 **GPU·인력 부담**이 큼  

### 우리 시스템 한 장 흐름 (쉬운 말)

```text
[채팅 화면] Open WebUI
      ↓
[규칙 엔진] Pipelines = “관련 문서 찾기 → 답 쓰기” 안내
      ↓
[검색 창고] 문서 조각 저장소 (Chroma 등)
      ↓
[로컬 AI] Ollama = 우리 PC/서버 안의 답변 엔진
```

- 직원은 브라우저에서 채팅만 함  
- 인터넷 전체가 아니라 **우리가 넣은 사내 문서**만 봄  

### 환각(없는 말)을 줄이려는 시도 (한 줄)

- 답은 “기억”이 아니라 **찾아온 문서 조각**을 근거로 쓰게 하고, 근거가 없으면 **확인을 요청**하거나 “모른다”에 가깝게 말하게 함

# 2. 하네스 엔지니어링으로 관리한 프로젝트 구조

> **30초 요약:**  
> AI에게 일을 맡기되, **안전벨트·채점표·역할 분담**을 씌워 “혼자 추측으로 합격”하지 못하게 했습니다.

### 하네스란?

- **하네스** = AI가 날뛰지 않게 씌운 **운영 장치**  
  - 안전벨트: 하지 말 것(비밀 커밋 금지, 추측 합격 금지 등)  
  - 채점표: “이게 되면 통과”라는 **수용 기준**  
  - 역할 분담: 기획 / 구현 / 검사 분리  

### 역할 분담 (발표용 이름)

| 역할 | 하는 일 | 비유 |
|------|---------|------|
| **기획(pl)** | 목표·범위·통과 기준 정리, 전체 진행 | 감독 |
| **개발(developer)** | 실제로 고치고 테스트 | 선수 |
| **검증(verifier)** | 개발자 말이 아니라 **결과물·로그**로 다시 확인 | 심판 |

- 검증이 “다시 고치라(REVISE)”면 → **실패 이유**를 공용 노트(`PL_FAILURE_LOG`)에 남기고 재도전  
- “됐을 것 같다”만으로 끝내지 않음  

### 폴더 큰 그림 (쉬운 말)

| 위치 | 쉬운 설명 |
|------|-----------|
| `rag/pipelines` | 질문 → 문서 찾기 → 답 쓰기 **규칙** |
| `rag/data/docs` | 매뉴얼·스펙 **원본 파일** |
| `rag/scripts` | 문서 등록(인덱싱), 자동 시험·채점 |
| `docker-compose` | 채팅 화면, 규칙 엔진, (GPU) 로컬 AI, DB 등을 **한번에 켜는 설계도** |
| `.cursor` agents / skills | AI 작업자에게 주는 **역할·안내서** |
| `AGENTS.md` / `PL_FAILURE_LOG.md` | 팀 규칙 + **실패에서 배운 점** 기록 |

### 왜 이렇게 나눴나?

- 품질이 떨어지면 **느낌으로 합격**시키지 않음  
- “통과 증거”를 파일로 남김 (답 원문, 시험 결과 등 → artifact)  
- 같은 실수가 반복되면 실패 로그에 적어 **다음에 또 안 하게** 함

# 3. 실제 변경 및 개선된 내역

> **30초 요약:**  
> **더 빨리** 답하고, **문서에 맞게** 답하며, **앞 대화를 이어서** 정리·표 요청을 이해하게 만들었습니다. 한계도 솔직히 말합니다.

## 3-0. 검색의 진화 — Hybrid & Reranker (슬라이드 7–9 대본)

> **발표용 한 줄:**  
> 뜻만 보던 검색에서, **단어까지 잡고 → 순위를 합치고 → 수석 사서가 다시 채점**하는 검색으로 키웠습니다.

### 대본 (그대로 읽어도 됨)

초기에 우리는 **벡터 검색**만 썼습니다.  
질문을 BGE-M3 임베딩 모델로 **숫자 좌표**로 바꾸고, 문서 조각과도 같은 방식으로 좌표를 만든 뒤, **코사인 유사도**로 가까운 조각을 찾는 방식입니다.  
쉬운 말로 하면 “뜻이 비슷한 글을 찾는 검색”입니다.

그런데 이 방식만으로는 **파일 경로**나 **제품명·명령 코드** 같은 **고유명사** 적중률이 많이 떨어졌습니다.  
의미가 비슷한 문장은 잘 가져와도, `D:\nsis\...` 같은 **정확한 문자열**은 약했습니다.

그래서 **BM25 키워드 검색**을 더했습니다.  
“뜻이 비슷한지”에 더해, “같은 단어·코드가 들어있는지”를 함께 보는 것입니다.  
그리고 두 검색의 순위표를 **RRF(Reciprocal Rank Fusion)** 로 수학적으로 합쳐, 한 쪽만 잘 맞춘 문서가 빠지지 않게 했습니다.  
이게 **하이브리드 검색**입니다.

여기까지가 “후보를 넓고 균형 있게 모으는” 단계라면, 마지막에는 **Reranker**, 비유하자면 **수석 사서**를 두었습니다.  
모아 둔 후보를 “이 질문의 문맥에 정말 맞는지” 한 번 더 정밀 채점해서, **가장 중요한 문서가 1등**으로 올라오게 했습니다.

**그 결과, 골든 질문 평가에서 기대 문서(출처) 적중은 24/24(100%), 필수 키워드 적중은 79/80(약 99%)까지 확인했습니다.**  
경로·배치 파일명·API 이름처럼 예전에 약하던 고유 문자열도 같은 평가에서 맞춰졌고, 이런 항목을 계속 늘려 회귀 테스트도 **약 137개**까지 키워 품질을 잠갔습니다.

### 슬라이드에 넣을 숫자 (근거)

| 지표 | 수치 | 출처 메모 |
|------|------|-----------|
| 출처 적중 | **24/24 (100%)** | `rag/data/eval/artifacts/22_post_eval_related.txt` |
| 키워드 적중 | **79/80 (약 99%)** | 동일 (항목 성공=출처+키워드 전부) |
| 항목 통과 | 23/24 | 동일 (1건은 비대상/기존 실패 메모) |
| 회귀 테스트 | **약 137/137** | `CHANGELOG.md` / `RAG_PIPELINE_GUIDE.md` |
| 골든 질문 규모 | **52문항** | `golden_questions.json` (현재) |

> 진행자 참고: 저장소에는 “벡터만 vs 하이브리드” **동일 조건 A/B %** 기록은 없었습니다.  
> 위 수치는 **하이브리드(+리랭크) 체계**에서 돌린 골든 검색 평가 결과입니다. 초기는 체감(경로·제품명 빗나감)으로 말씀하시고, 수치로 잠근 결과는 이 표로 끝맺으시면 됩니다.

### 발표 포인트 (불릿)

- **벡터만:** 질문 → BGE-M3 좌표 → 코사인 유사도 → 가까운 청크  
- **한계:** 경로·파일명·API 코드 등 고유 문자열 약함  
- **Hybrid:** 벡터 + BM25 → **RRF**로 순위 병합  
- **Reranker:** 후보를 질문과 다시 채점해 1등 문서 선별 (“수석 사서”)  
- **수치 마무리:** 출처 **100%(24/24)**, 키워드 **약 99%(79/80)**  

## 3-1. 속도 (체감)

### 발표 포인트

- **예전:** 질문 하나당 답이 끝나기까지 **대략 2~3분** 걸리기도 함  
- **개선 후 (워밍업된 상태, warm):**  
  - 짧은 사실 질문: **수 초** 수준  
  - 긴 절차 설명: **대략 수십 초 안쪽**을 목표로 맞춤  
- **어떻게?**  
  - 로컬 AI를 **GPU**로 돌림  
  - 불필요하게 무거운 단계(예: 매번 긴 재작성·무거운 재정렬)를 줄임  
- **솔직한 한계**  
  - **첫 질문(cold)** 이나 서비스 막 켠 직후는 여전히 느릴 수 있음 (모델·검색기 로딩)  
  - 사람 여러 명이 **동시에** 몰리면 대기 시간이 늘 수 있음 (완전 해결은 아님)  

## 3-2. 답변 품질 (문서에 맞게)

### 발표 포인트

- **절차형 매뉴얼**  
  - 서로 다른 메뉴/경로를 섞어 말하던 것을, 문서에 적힌 **올바른 순서·메뉴명** 기준으로 맞춤  

- **스펙·표**  
  - 표가 일부만 나오거나 “없다”고 빗나가던 문제를 고쳐, 문서의 **해당 구간 전체**가 나오게 함  

- **API 문서**  
  - URL만 나오고 스키마가 빠지던 경우, **API 문서 기준**으로 경로와 필드를 함께 안내  

- **주제가 다른 문서 혼입 감소**  
  - 질문의 문서 종류(가이드/설치/API 등)에 맞게 검색 범위를 좁힘  

## 3-3. 대화 문맥 (“이어서 물어보기”)

### 발표 포인트

- 예: 한 주제를 설명한 뒤  
  - 「표로 정리해줘」「더 보기 쉽게」  
  → **앞 대화의 그 주제**를 표/단계로 다시 정리 (다른 문서로 새 주제 시작하지 않음)  

- 주제를 알 수 없을 때  
  → **“무엇을 정리할지 알려 달라”**고 확인 요청  
  → 아무 문서나 끌어와 채우지 않음  

## 3-4. 샘플 문서 데모

### 발표 포인트

- 공개 저장소에는 `sample_*.md` 같은 **가상 샘플 문서**만 둡니다  
- 실서비스에서는 로컬/비공개로 사내 문서를 넣고 인덱싱합니다  
- 인물·스펙·API 질문은 **샘플 문서 내용**으로 데모할 수 있습니다 

## 3-5. 실패에서 배운 것 (짧게)

### 발표 포인트

- 짧은 질문이 “이어지는 질문”으로 **잘못 인식**되어 앞 대화에 끌려감 → 고침  
- 「표로」만 보면 **미디어 서버 표로 고정**하던 버그 → 주제별로 가드  
- 「표를 활용해서 더 보기 쉽게」처럼 **비슷한 말투 변형**도 놓치지 않게 보강  
- 이런 실수를 **실패 로그**에 남겨, 다음에 같은 함정을 피함

# 5. 예상 Q&A (쉬운 답)

**Q1. 우리 회사 데이터가 바깥으로 나가나요?**  
A. 이 구성의 답변 엔진은 **로컬(Ollama)** 쪽을 쓰는 흐름입니다. 사내 문서는 우리가 넣은 저장소에서 찾고, “인터넷에 물어보는 검색”이 아닙니다. (세부 보안·네트워크 정책은 인프라 담당 기준을 따르면 됩니다.)

**Q2. 매뉴얼을 고치면 AI를 다시 학습해야 하나요?**  
A. **아니요(RAG).** 보통은 문서를 넣고 **인덱싱(검색용으로 정리)**만 다시 하면 됩니다. 학습처럼 모델을 통째로 다시 가르치지 않습니다.

**Q3. 답이 틀리면 어떻게 하나요?**  
A. 출처를 보고 문서를 고치거나, “이 질문은 이렇게 답해야 한다”는 **시험 문제(골든)**와 자동 시험을 늘려 재발을 막습니다. 실패 로그에도 남깁니다.

**Q4. ChatGPT랑 뭐가 다른가요?**  
A. 일반 챗봇은 넓은 상식에 강하고, 우리는 **우리 매뉴얼을 찾아 근거를 붙인 답**에 초점을 둡니다. “사내 절차·스펙”에 더 맞춰져 있습니다.

**Q5. 왜 가끔 첫 질문이 느린가요?**  
A. 엔진·검색기가 **처음 켜질 때 준비**하느라 그렇습니다. 워밍업 뒤에는 훨씬 빨라지는 편이고, 동시 사용자가 많으면 또 기다릴 수 있습니다.
