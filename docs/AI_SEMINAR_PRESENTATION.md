# 사내 문서 도우미(RAG) — AI 세미나 발표 노트

**대상:** 비전공자 포함 전체  
**분량:** 약 15~20분  
**프로젝트:** Open WebUI + 로컬 AI(Ollama) + 사내 문서 검색(RAG)

---

## 발표 흐름 (목차)

1. RAG와 “AI를 다시 학습시키는 것”의 차이  
2. 하네스 엔지니어링으로 관리한 프로젝트 구조  
3. 실제로 바뀐 점·좋아진 점  
4. 예상 질문(Q&A)

# 1. RAG와 AI 모델을 학습시키는 것의 차이

> **30초 요약:**  
> 우리는 AI에게 매뉴얼을 **외우게** 하지 않고, 질문할 때마다 **참고서를 펼쳐 보게** 했습니다. 그게 RAG입니다.

### 발표 포인트

- **RAG** = Retrieval-Augmented Generation  
  - 쉬운 말: **시험 볼 때 참고서를 펼쳐 보고 답하는 것**  
  - 매뉴얼·스펙 파일은 그대로 두고, 질문마다 “관련 페이지”를 찾아 붙여서 답을 만듦  
  - 답 옆에 **어느 문서에서 봤는지(출처)**를 달 수 있음

- **학습(파인튜닝·재학습)** = 모델 속을 바꾸는 것  
  - 쉬운 말: **참고서 내용을 머릿속에 다시 외우게 가르치는 것**  
  - 시간이 오래 걸리고, 좋은 학습 데이터·큰 GPU 비용이 필요함  
  - 매뉴얼이 자주 바뀌면 **또 다시 가르쳐야** 함

| 비교 | RAG (참고서) | 재학습 (외우기) |
|------|--------------|----------------|
| 문서가 바뀌면 | 문서만 다시 넣으면 됨 | 보통 다시 학습 |
| 출처 표시 | 하기 쉬움 | 어렵거나 불명확 |
| 비용·시간 | 상대적으로 적음 | 큼 |
| 이 프로젝트 | **선택** | 부담이 커서 비선택 |

### 우리가 RAG를 고른 이유 (한 줄씩)

- 사내 매뉴얼·스펙이 **자주 바뀜** → 외우게 하면 따라가기 힘듦  
- 직원에게 **“어디서 나온 말인지”**가 중요함  
- 큰 모델을 사내에서 매번 재학습하기엔 **GPU·인력 부담**이 큼  

### 우리 시스템 한 장 흐름 (쉬운 말)

```text
[채팅 화면] Open WebUI
      ↓
[규칙 엔진] Pipelines = “관련 문서 찾기 → 답 쓰기” 안내
      ↓
[검색 창고] 문서 조각 저장소 (Chroma 등)
      ↓
[로컬 AI] Ollama = 우리 PC/서버 안의 답변 엔진
```

- 직원은 브라우저에서 채팅만 함  
- 인터넷 전체가 아니라 **우리가 넣은 사내 문서**만 봄  

### 환각(없는 말)을 줄이려는 시도 (한 줄)

- 답은 “기억”이 아니라 **찾아온 문서 조각**을 근거로 쓰게 하고, 근거가 없으면 **확인을 요청**하거나 “모른다”에 가깝게 말하게 함

# 2. 하네스 엔지니어링으로 관리한 프로젝트 구조

> **30초 요약:**  
> AI에게 일을 맡기되, **안전벨트·채점표·역할 분담**을 씌워 “혼자 추측으로 합격”하지 못하게 했습니다.

### 하네스란?

- **하네스** = AI가 날뛰지 않게 씌운 **운영 장치**  
  - 안전벨트: 하지 말 것(비밀 커밋 금지, 추측 합격 금지 등)  
  - 채점표: “이게 되면 통과”라는 **수용 기준**  
  - 역할 분담: 기획 / 구현 / 검사 분리  

### 역할 분담 (발표용 이름)

| 역할 | 하는 일 | 비유 |
|------|---------|------|
| **기획(pl)** | 목표·범위·통과 기준 정리, 전체 진행 | 감독 |
| **개발(developer)** | 실제로 고치고 테스트 | 선수 |
| **검증(verifier)** | 개발자 말이 아니라 **결과물·로그**로 다시 확인 | 심판 |

- 검증이 “다시 고치라(REVISE)”면 → **실패 이유**를 공용 노트(`PL_FAILURE_LOG`)에 남기고 재도전  
- “됐을 것 같다”만으로 끝내지 않음  

### 폴더 큰 그림 (쉬운 말)

| 위치 | 쉬운 설명 |
|------|-----------|
| `rag/pipelines` | 질문 → 문서 찾기 → 답 쓰기 **규칙** |
| `rag/data/docs` | 매뉴얼·스펙 **원본 파일** |
| `rag/scripts` | 문서 등록(인덱싱), 자동 시험·채점 |
| `docker-compose` | 채팅 화면, 규칙 엔진, (GPU) 로컬 AI, DB 등을 **한번에 켜는 설계도** |
| `.cursor` agents / skills | AI 작업자에게 주는 **역할·안내서** |
| `AGENTS.md` / `PL_FAILURE_LOG.md` | 팀 규칙 + **실패에서 배운 점** 기록 |

### 왜 이렇게 나눴나?

- 품질이 떨어지면 **느낌으로 합격**시키지 않음  
- “통과 증거”를 파일로 남김 (답 원문, 시험 결과 등 → artifact)  
- 같은 실수가 반복되면 실패 로그에 적어 **다음에 또 안 하게** 함

# 3. 실제 변경 및 개선된 내역

> **30초 요약:**  
> **더 빨리** 답하고, **문서에 맞게** 답하며, **앞 대화를 이어서** 정리·표 요청을 이해하게 만들었습니다. 한계도 솔직히 말합니다.

## 3-1. 속도 (체감)

### 발표 포인트

- **예전:** 질문 하나당 답이 끝나기까지 **대략 2~3분** 걸리기도 함  
- **개선 후 (워밍업된 상태, warm):**  
  - 짧은 사실 질문: **수 초** 수준  
  - 긴 절차 설명: **대략 수십 초 안쪽**을 목표로 맞춤  
- **어떻게?**  
  - 로컬 AI를 **GPU**로 돌림  
  - 불필요하게 무거운 단계(예: 매번 긴 재작성·무거운 재정렬)를 줄임  
- **솔직한 한계**  
  - **첫 질문(cold)** 이나 서비스 막 켠 직후는 여전히 느릴 수 있음 (모델·검색기 로딩)  
  - 사람 여러 명이 **동시에** 몰리면 대기 시간이 늘 수 있음 (완전 해결은 아님)  

## 3-2. 답변 품질 (문서에 맞게)

### 발표 포인트

- **단말기 사용자 관리**  
  - 잘못된 페이지·메뉴를 섞어 말하던 것을, 매뉴얼의 **올바른 메뉴** 기준으로 맞춤  

- **사용자를 단말기에 넣는 방법**  
  - 문서에 있는 **서로 다른 3가지 경로**를 구분해서 설명  
    1. 사용자 관리 쪽  
    2. 단말기 사용자 관리 쪽  
    3. 단말기 사용자 확장(여러 대에 보내기) 쪽  
  - + **자동 동기화** 설정도 같은 맥락에서 안내  

- **자동 빌드(설치 패키지)**  
  - “자동화 버전” 절차를 **빠짐없이** 말하도록 보강 (수동 클릭 절차와 섞지 않기)  

- **미디어 서버 스펙**  
  - 카메라 대수별 권장 표 **전체 구간**이 나오게 (일부만 나오거나 “스펙 없다”고 User Guide로 빗나가던 문제 수정)  

- **API(FaceWT 등)**  
  - 스키마·API 질문은 **API 문서** 기준으로, 엉뚱한 스펙 표로 바꾸지 않음  

## 3-3. 대화 문맥 (“이어서 물어보기”)

### 발표 포인트

- 예: 자동 빌드 설명을 들은 뒤  
  - 「표로 정리해줘」「표를 활용해서 더 보기 쉽게」  
  → **앞의 자동 빌드**를 표/단계로 다시 정리 (다른 매뉴얼로 새 주제 시작하지 않음)  

- 예: API 스키마 이야기 뒤에 「표로」  
  → **그 스키마 표** (미디어 서버 하드웨어 표로 바꾸지 않음)  

- 주제를 알 수 없을 때  
  → **“무엇을 정리할지 알려 달라”**고 확인 요청  
  → 아무 문서나 끌어와 채우지 않음  

## 3-4. 인물 정보 (샘플 문서)

### 발표 포인트

- `Test.md` 같은 **인물 프로필** 문서 기준  
- 「박준언, 방인재에 대해」처럼 **여러 이름**을 한 번에 물어도 각각 맞춤  
- 카메라·저장장치 설명 등 **무관한 내용이 섞이지 않게**  

## 3-5. 실패에서 배운 것 (짧게)

### 발표 포인트

- 짧은 질문이 “이어지는 질문”으로 **잘못 인식**되어 앞 대화에 끌려감 → 고침  
- 「표로」만 보면 **미디어 서버 표로 고정**하던 버그 → 주제별로 가드  
- 「표를 활용해서 더 보기 쉽게」처럼 **비슷한 말투 변형**도 놓치지 않게 보강  
- 이런 실수를 **실패 로그**에 남겨, 다음에 같은 함정을 피함

# 5. 예상 Q&A (쉬운 답)

**Q1. 우리 회사 데이터가 바깥으로 나가나요?**  
A. 이 구성의 답변 엔진은 **로컬(Ollama)** 쪽을 쓰는 흐름입니다. 사내 문서는 우리가 넣은 저장소에서 찾고, “인터넷에 물어보는 검색”이 아닙니다. (세부 보안·네트워크 정책은 인프라 담당 기준을 따르면 됩니다.)

**Q2. 매뉴얼을 고치면 AI를 다시 학습해야 하나요?**  
A. **아니요(RAG).** 보통은 문서를 넣고 **인덱싱(검색용으로 정리)**만 다시 하면 됩니다. 학습처럼 모델을 통째로 다시 가르치지 않습니다.

**Q3. 답이 틀리면 어떻게 하나요?**  
A. 출처를 보고 문서를 고치거나, “이 질문은 이렇게 답해야 한다”는 **시험 문제(골든)**와 자동 시험을 늘려 재발을 막습니다. 실패 로그에도 남깁니다.

**Q4. ChatGPT랑 뭐가 다른가요?**  
A. 일반 챗봇은 넓은 상식에 강하고, 우리는 **우리 매뉴얼을 찾아 근거를 붙인 답**에 초점을 둡니다. “사내 절차·스펙”에 더 맞춰져 있습니다.

**Q5. 왜 가끔 첫 질문이 느린가요?**  
A. 엔진·검색기가 **처음 켜질 때 준비**하느라 그렇습니다. 워밍업 뒤에는 훨씬 빨라지는 편이고, 동시 사용자가 많으면 또 기다릴 수 있습니다.

# 발표 팁 (진행자용)

1. **비유를 먼저, 용어는 나중에** — “참고서 vs 외우기”로 1분 잡고 RAG를 소개하세요.  
2. **라이브는 짧게** — “자동빌드 → 표로 정리” 또는 “미디어 서버 스펙” 한 번이면 문맥·품질이 잘 보입니다.  
3. **한계를 먼저 말해 신뢰** — cold start·동시 접속을 숨기지 않으면 Q&A가 수월합니다.  
4. 슬라이드로 옮길 때: 각 섹션의 **30초 요약 + 불릿 5개**만 옮겨도 충분합니다.
